# MiniSQL 桌面 GUI 设计

## 1. 目标

为 MiniSQL 增加一个基于 Python 3.11 标准库 `tkinter` 和 `ttk` 的 Windows
桌面程序。GUI 应覆盖 MiniSQL 当前能够通过 `MiniDB` 执行的全部 SQL 操作，展示
结构化查询结果、编译或执行错误、原始逻辑计划和优化后逻辑计划，并作为课程验收
中的独立亮点功能进行演示。

第一版定位为轻量版 DataGrip：既提供 SQL 工作台，也提供新建表、删除表、浏览
数据、新增行、修改行和删除行的图形化入口。所有写操作都生成 SQL，并通过正常的
MiniSQL 编译和执行链完成；GUI 不直接修改 Catalog、页面或数据文件。

## 2. 范围

### 2.1 第一版包含

- 打开或切换 MiniSQL 数据目录；
- 浏览当前数据库中的表、字段和字段类型；
- 通过对话框新建表，并预览生成的 `CREATE TABLE`；
- 通过对象树右键菜单打开数据、刷新或删除表；
- 在数据编辑器中新增、修改和删除行；
- 使用多个 SQL 控制台标签页；
- 编辑并执行一条或多条以分号结束的 SQL；
- 使用 `Ctrl+Enter` 执行 SQL；
- 用表格展示查询结果，用消息展示非查询语句的执行结果；
- 展示原始逻辑计划、优化后逻辑计划和计划 JSON；
- 展示词法、语法、语义、存储和执行错误的类型、位置与原因；
- 将带位置的错误定位到 SQL 编辑器对应行列；
- 在后台工作线程中运行编译和执行流程，避免阻塞 Tk 主线程；
- 在关闭窗口或切换数据目录时安全关闭 `MiniDB` 并写回脏页。

### 2.2 第一版不包含

- `ALTER TABLE`、索引、外键和表结构设计器；
- 多个数据库连接并行运行；
- 用户、权限、网络连接或远程数据库；
- SQL 自动补全、语法高亮和代码格式化；
- 查询成本估计、物理执行计划或运行时性能剖析；
- Web 服务、第三方 GUI 框架或第三方图形库。

`DROP TABLE` 和 `LIMIT` 已接通执行链，可由 GUI 使用。`UPDATE` 只在执行器接通后
启用图形化修改；接通前按钮保持禁用并说明原因。GUI 不捕获并伪装未实现错误，也
不在界面层补写数据库执行逻辑。

## 3. 界面设计

主窗口采用 SQL Studio 工作台布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ 数据目录  刷新  执行 SQL  清空编辑器                 状态 │
├────────────────┬─────────────────────────────────────────────┤
│ 对象浏览器     │ SQL 控制台 1 | SQL 控制台 2 | +             │
│                │                                             │
│ ▾ student      │ SELECT name FROM student                    │
│   id INT       │ WHERE age > 18;                             │
│   name VARCHAR │                                             │
│                ├─────────────────────────────────────────────┤
│ ▸ course       │ 数据 | 原始计划 | 优化后计划 | JSON | 消息 │
│                │                                             │
└────────────────┴─────────────────────────────────────────────┘
```

- 左侧使用 `ttk.Treeview` 展示数据目录、表和列；
- 对象树提供新建表、打开数据、刷新和删除表的右键菜单；
- 右上使用 `ttk.Notebook` 管理多个 `tk.Text` SQL 控制台；
- 右下使用 `ttk.Notebook` 管理五个结果标签页；
- 查询结果使用 `ttk.Treeview`，列由结构化结果动态创建；
- 数据结果上方提供新增行、修改行、删除行和刷新按钮；
- 原始计划与优化后计划采用独立标签页切换，不在第一版实现计划差异算法；
- 计划树第一版使用等宽文本展示 `plan_to_tree()` 的结果；
- 状态栏显示当前数据目录、执行状态、耗时和返回行数；
- 运行期间禁用重复执行和数据目录切换操作。

### 3.1 图形化操作规则

- 新建表对话框收集表名、字段名和 `INT`/`VARCHAR(n)` 类型，生成并执行
  `CREATE TABLE`；
- 打开表数据生成 `SELECT * FROM <table> LIMIT 200`，避免一次加载过多记录；
- 新增行根据完整表模式生成 `INSERT`，字符串使用 SQL 单引号转义；
- 修改行生成 `UPDATE ... SET ... WHERE ...`；执行器未支持 `UPDATE` 时禁用；
- 删除选中行生成带完整旧行条件的 `DELETE`。由于当前系统没有主键，该条件可能
  删除内容完全相同的多行，确认框必须明确展示 SQL 和这一风险；
- 删除表显示生成的 `DROP TABLE` 并要求二次确认；
- 所有生成 SQL 都写入消息日志，便于课堂解释和问题复现。

## 4. 架构

采用 GUI、控制器、后台工作线程和数据库核心四层结构：

```text
Tkinter View
    ↓ GuiCommand
GuiController
    ↓ WorkerRequest
DatabaseWorker（唯一 MiniDB 所有者）
    ↓
MiniDB.execute_detailed()
    ↓
Lexer → Parser → Semantic → Planner → Optimizer → Executor
    ↓ ExecutionBatch
GuiController
    ↓ Tk.after() 在主线程更新
Tkinter View
```

建议新增以下模块：

```text
database_system/gui/
├── __init__.py
├── app.py          # 主窗口、控件和 Tk 事件
├── controller.py   # GUI 命令编排和展示模型转换
├── models.py       # GUI 与引擎之间的结构化结果类型
└── worker.py       # 单工作线程、请求队列和响应队列
```

GUI 不直接访问 Page、BufferPool、StorageEngine 或 Executor。它只通过新增的结构化
执行入口访问 `MiniDB`，从而保持模块边界清晰。

## 5. 结构化执行接口

现有 `MiniDB.execute(sql) -> str` 必须保留，CLI 行为不得改变。为 GUI 增加一个
向后兼容的入口：

```python
MiniDB.execute_detailed(sql: str) -> ExecutionBatch
```

`ExecutionBatch` 包含按源码顺序排列的 `StatementResult`。每个结果至少包含：

- 原始语句的序号和 AST 类型；
- 是否成功；
- 查询列名与行数据，或非查询语句的消息；
- 原始计划树和计划 JSON；
- 优化后计划树和计划 JSON；
- 执行耗时；
- 失败时的错误类型、行、列和消息。

多语句输入逐条处理并保留每条语句的独立结果。第一条失败后停止执行后续语句，
避免用户误以为一个包含错误的批次已全部完成；已成功执行的前序语句不自动回滚，
这与当前 MiniSQL 没有事务支持的事实一致。

查询列名由已分析 AST 和 Catalog 模式生成：显式投影使用投影列名，`SELECT *`
使用表模式列名，`SHOW DATABASES` 和 `SHOW TABLES` 使用固定展示列名。不得通过
解析 CLI 格式化字符串推断表格结构。

该接口涉及成员 D 负责的 `MiniDB`，实现和合入前需要 D 复核。它是新增接口，
不会修改冻结契约中已有方法的参数或返回值。

## 6. 并发与生命周期

`MiniDB` 面向单用户、单进程场景，GUI 只创建一个后台工作线程，并让该线程独占
当前 `MiniDB` 实例。所有 SQL 执行、数据目录切换和关闭操作按请求队列串行处理。

Tk 主线程只负责界面事件和绘制。后台线程不得直接访问 Tk 控件；它将结果写入响应
队列，主线程使用 `root.after()` 定期取回结果并更新界面。

切换数据目录时按以下顺序执行：

1. 禁用执行和目录切换按钮；
2. 等待当前 SQL 请求结束；
3. 在工作线程中关闭当前 `MiniDB`；
4. 使用新目录创建 `MiniDB`；
5. 刷新对象浏览器；
6. 恢复界面操作。

关闭窗口时向工作线程发送关闭请求，等待脏页写回和文件关闭完成后再销毁主窗口。
第一版不提供强制中断正在执行的 Python 代码；“关闭”应等待当前短任务自然结束。

## 7. 错误处理

- `MiniSQLError` 的类型、行、列和消息以结构化字段返回；
- GUI 在“消息”标签显示完整错误，并自动切换到该标签；
- 有源码位置时，在 SQL 编辑器中选中对应字符并滚动到可见位置；
- 没有源码位置的存储或系统错误显示错误类型和消息，不虚构行列；
- 未支持的计划节点显示 `ExecError`，不能退化为成功或静默忽略；
- 工作线程捕获未预期异常并转换为内部错误响应，保证 Tk 事件循环不退出，同时保留
  可用于调试的异常信息；
- 打开无效数据目录失败时继续保留原数据库连接，不留下半切换状态。

## 8. 查询计划展示

对于能够生成计划的语句，GUI 同时保留优化前和优化后的计划：

- “原始计划”展示 Planner 直接产生的计划树；
- “优化后计划”展示 Optimizer 处理后实际交给 Executor 的计划树；
- “JSON”默认展示优化后计划 JSON，并提供原始或优化后选择；
- 没有产生关系计划的操作仍可展示对应的单节点计划；
- 如果优化前后相同，界面明确显示“本语句未产生可见优化”，不暗示优化失败。

演示用例应包含可观察的常量折叠和布尔化简，例如：

```sql
SELECT name FROM student WHERE 1 = 1 AND age > 10 + 8;
```

## 9. 测试策略

严格采用测试先行：

1. `models` 测试结构化结果和错误字段；
2. `MiniDB.execute_detailed()` 测试单语句、多语句、查询列名、计划和错误定位；
3. `GuiController` 使用假 Worker 测试执行、忙状态、结果选择和目录切换；
4. `DatabaseWorker` 使用假 MiniDB 测试请求串行化、响应和安全关闭；
5. Tk 冒烟测试创建窗口、执行一次假请求并销毁窗口，不依赖人工点击；
6. 端到端测试覆盖当前所有已支持 SQL，并验证错误不会终止 GUI；
7. 运行角色 A 的 Lexer/Parser 回归和完整测试集，确认 GUI 没有改变已有编译器行为。

界面测试重点检查状态和数据，不依赖像素截图或特定 Windows 字体尺寸，以减少不同
环境下的脆弱失败。

## 10. 验收标准

- Windows 上可用一条仓库命令启动 GUI，不要求安装第三方包；
- 当前 MiniSQL 已支持的 SQL 均可从编辑器执行；
- 查询结果以正确列名和行数据显示；
- 非查询语句显示明确的成功信息和受影响行数；
- 编译或执行错误不会关闭窗口，并能显示和定位错误；
- 原始计划、优化后计划和 JSON 均可查看；
- 执行 SQL 时窗口仍可重绘，不出现重复执行；
- 切换目录和关闭窗口会安全关闭数据库；
- 现有 CLI 与测试行为保持兼容；
- `DROP TABLE`、`UPDATE`、`LIMIT` 未接通执行层时明确报错，接通后无需修改 GUI
  即可正常展示结果。

## 11. 职责与评审

- 成员 A 负责 GUI 展示、控制器、计划展示和相应测试；
- `MiniDB.execute_detailed()` 属于与成员 D 的最小集成点，必须由 D 复核；
- 不修改成员 B 负责的 Plan 节点或 Optimizer 规则；
- 不修改成员 C 负责的页式存储和缓存算法；
- 如结构化接口需要进入冻结契约，必须经过全组评审后再更新契约。
